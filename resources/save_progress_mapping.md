# The Artisan of Glimmith — 세이브 파일 진행도 ↔ 게임 지역 매칭 분석

세이브 파일 조사 결과. 목표: 세이브 파일만 보고 플레이어가 게임 내 어느 지역(다리/전망대/장터/마을/숲/성/나선형 섬/한적한 정원)에 도달했는지 알아낼 수 있는가?

**결론: 가능하다.** 세이브 파일에 퍼즐 완료 상태가 `Zone/규칙폴더/파일명` 전체 경로로 그대로 저장되어 있어서, 폴더별 진행률을 직접 집계할 수 있고, 이 규칙폴더는 나무위키 문서의 지역 구분과 상당히 신뢰도 높게 대응시킬 수 있다.

---

## 1. 세이브 파일 위치 (Steam Proton, Linux)

```
~/.steam/debian-installation/steamapps/compatdata/4160210/pfx/drive_c/users/steamuser/AppData/Local/Geri/Saved/SaveGames/
  SaveFile1.sav            # 메인 세이브 (최신)
  SaveFile1_backup_1~10.sav  # 자동 백업 (숫자가 클수록 더 오래된 스냅샷)
  SaveFile2.sav             # 별도 슬롯
  Settings.sav              # 설정
```

Windows라면 `%LOCALAPPDATA%\Geri\Saved\SaveGames\`에 해당. App ID는 `4160210`.

이 저장소의 `saves/` 폴더에 위 파일들을 복사해두었다.

## 2. 세이브 파일 포맷

표준 Unreal Engine `GVAS` SaveGame 포맷 (UE 4.27, `SaveGameFileVersion=2`).

- 헤더: `GVAS` 매직 → SaveGameFileVersion(int32) → PackageFileUEVersion(int32) → FEngineVersion(major/minor/patch/changelist + branch FString `++UE4+Release-4.27`) → CustomVersion 배열 → SaveGameClass 이름 → 태그드 프로퍼티 목록
- 퍼즐 진행 데이터는 `TMap<FString, FPuzzleSaveData>` 형태의 프로퍼티로, 키는 퍼즐 파일 경로, 값은 아래 구조체.

### 퍼즐별 저장 구조체 (관찰된 필드)

```
PuzzleID        : StrProperty   = "AGeri/Puzzles/Zone3/5-inequality/0123.puz"  (TMap 키와 동일한 값 중복 저장)
PuzzleVersion   : IntProperty
HasBeenSolved   : BoolProperty
HasBeenOpened   : BoolProperty
CellColors      : ArrayProperty<IntProperty>   # 그리드 칸 색칠 상태
StableComponentIDs : ArrayProperty<IntProperty>
EdgeStates      : ArrayProperty<EnumProperty EEdgeState>  # Null/Border/NoBorder/GivenBorder
...
None            # 구조체 종료
```

**핵심**: `PuzzleID` 문자열 안에 `Zone1/2-shape-bank`, `Zone3/5-inequality` 같은 개발 시점 폴더 경로가 그대로 남아 있다. 즉 세이브 파일 자체가 "이 플레이어가 어떤 규칙 폴더의 퍼즐을 만졌는가"를 직접 알려준다 — 별도의 매핑 없이도 폴더 단위 진행률 집계가 가능하다.

바이트 오프셋 파싱 로직: `PuzzleID\0` 태그(이름 길이 프리픽스 4바이트 포함, 9=len("PuzzleID")+1) 앞에 있는 FString이 TMap 키(퍼즐 경로)다. `HasBeenSolved\0...BoolProperty\0` 뒤 8바이트(Size int32=0, ArrayIndex int32=0)를 건너뛰면 다음 1바이트가 bool 값이다.

**실제 플레이로 확인된 추가 사실 (2026-09-18)**: 퍼즐을 **열기만 해도**(풀지 않아도) 즉시 세이브에 항목이 생성된다 (`HasBeenSolved=0`, `HasBeenOpened=1`). 따라서 "이 폴더에 도달했는가"를 판정할 때는 `solved` 개수가 아니라 **entry 존재 여부(=encountered) 자체**를 프론티어 신호로 써야 한다 — 플레이어가 다음 지역 퍼즐을 미리 한 번 열어만 봐도 그 지역이 세이브에 나타난다.

## 3. 실제 파싱 결과 — 세이브만으로 진행 프론티어 추적

`SaveFile1_backup_10.sav`(더 이전 스냅샷) vs `SaveFile1.sav`(최신)를 같은 방식으로 파싱해 비교:

| 규칙 폴더 | backup_10 (이전) | SaveFile1 (최신) | 해석 |
|---|---|---|---|
| Zone1/1-single-shape ~ Zone2/9-no-rectangles | 대부분 완료 또는 X/X | 동일 | Zone1·Zone2는 이미 프론티어를 지남 |
| Zone3/1-tatami | 15/15 | 15/15 | 완료 |
| Zone3/2-loopy | 22/26 | 22/26 | 진행 중(정체) |
| Zone3/3-vertex-radar | 16/16 | 16/16 | 완료 |
| **Zone3/4-difference** | **세이브에 등장조차 안 함** | **8/11 (신규 등장)** | 이 구간에서 새로 열림 |
| Zone3/5-inequality | 10/10 | 15/15 (총 개수 증가) | silver 클리어 후 gold/ruby 퍼즐이 추가로 열림 |
| Zone3/6-compass 이후 (compass, hedge maze, 나선형 섬, 한적한 정원) | 없음 | 없음 | 아직 미도달 |

→ 세이브 파일만으로 "이 플레이어는 지금 성 지역(Zone3) 안에서 difference/inequality 근방을 진행 중이며, 나침반·생울타리 미로·나선형 섬·한적한 정원은 미도달"이라는 결론을 **정확히** 재현했다. 각 폴더의 (total, solved) 카운트가 세이브 스냅샷 시점에 따라 예상대로 변하는 것도 확인됨 → 이 방식이 실제로 시간 흐름에 따른 진행을 추적한다는 검증.

파싱 스크립트: 정규식으로 `PuzzleID` 태그를 모두 찾고, 각 태그 앞의 FString(퍼즐 경로)과 근방의 `HasBeenSolved` bool 값을 읽어 `Zone/규칙폴더`별로 (encountered count, solved count)를 집계.

## 4. 나무위키 레벨 목록(3.1~3.9) 전체 대응표

나무위키 "레벨 목록" 섹션은 3.1~3.9의 9개 지역(+3.7 메타 항목, +3.10 총합)으로 구성된다. 아래는 그 9개 전부를 게임 파일의 `Zone{N}/{규칙폴더}`와 대조하고, **세이브 파일만으로 이 단계를 구분할 수 있는지**를 별도 컬럼으로 평가한 결과다.

범례 — **매핑 신뢰도**: 높음(폴더명 또는 퍼즐개수가 정확히 일치) / 중간(개수 근접 또는 부분 일치) / 낮음(추정만 가능, 미검증). **세이브 구분 가능성**: 세이브 파일에 해당 폴더 경로가 실제로 나타나는지와 무관하게, "이 폴더가 정확히 이 표시 지역이다"라고 자신 있게 라벨링할 수 있는지를 뜻함 — 폴더 단위 진행률 자체는 9개 지역 모두 항상 추적 가능하다 (경로 문자열이 그대로 세이브에 있으므로).

- **완전히 신뢰 가능 (화면 라벨로 확정)**: **다리(3.1)**, **전망대(3.2)**, **장터(3.3, 3/3)**, **마을(3.4, 4/4)**, **숲 지역(3.5, 10/10)**, **성 지역(3.6, 7/7)**, **나선형 섬(3.8)**, **한적한 정원(3.9)** → **나무위키 9개 지역 전부 실제 플레이로 확정 완료 (2026-09-18)**
- **물리적 지역이 아님 (메타 집계)**: 완벽한 윈도우(3.7) — 단, `7-finalboss`(final boss 특별 챌린지, 실제로는 `1152.puz` 1개뿐 — 이전에 3개로 잘못 기재했었음) 접근 지점을 겸함

즉 **다리→전망대→장터→마을→숲→성→나선형 섬→한적한 정원까지, 게임의 처음부터 끝(엔드게임 지역)까지 전체 진행 경로가 세이브 파일 폴더 구조와 완전히 1:1로 매핑됐다.** 세 가지 반복되는 게임 구조 패턴이 확인됨:
1. **같은 규칙 이름이 폴더 두 개로 나뉘면 합산된다** (예: 쌍둥이=`3`+`6`, 장미창=`4`+`7`)
2. **한 지역의 앞쪽 서브지역들을 전부 완료해야 마지막(관문 성격) 서브지역이 열린다** (장터: 두 갈래 완료→도형 창고, 마을: 세 서브지역 완료→숲길 입구)
3. **다음 지역 진입 시 여러 갈래(서브지역)가 동시에 개방된다** (장터: 2갈래, 성: 3갈래, 완벽한 윈도우: 2갈래)
4. **튜토리얼 팝업의 규칙 이름과 지역(창) 이름이 다를 수 있다** (`6-compass`의 첫인상은 "나침반"이었지만 실제 지역명은 "생울타리 미로")

남은 것은 **`FinalNote`/`FinalNote2`/`CompletionTracker` 엔딩 트리거의 실제 내용 확인**뿐이다.

나선형 섬(3.8)이나 다른 미검증 구간에도 이 패턴들이 있을 수 있으니 실제 도달 시 유의. 남은 것은 **마을→숲 전환 시점 검증**(장터처럼 숨은 추가 폴더가 있는지)과 **나선형 섬·한적한 정원의 실제 플레이 검증**뿐이다.

## 5. 진행 위치 산출 알고리즘 (제안)

1. 세이브 파일에서 모든 `PuzzleID` + `HasBeenSolved`/`HasBeenOpened`를 파싱
2. 경로를 `Zone{N}/{규칙폴더}`로 그룹핑, 폴더별 (encountered, solved) 집계
3. 폴더를 위 매핑 테이블로 "지역명"에 연결
4. **현재 위치** = 항목이 하나라도 있지만(`encountered > 0`) 아직 이 지역의 규칙 폴더 그룹 안에서 완전히 끝나지 않은 것 중 폴더 번호가 가장 큰 것 (= 프론티어)
5. **완료한 지역 목록** = 그 지역에 속한 모든 규칙 폴더가 `encountered == 이론상 총개수`이고 대부분 `solved`인 경우

- **세이브 파일 직접 편집 시 주의사항** (`set_solved.py` 사용 경험에서 확인):
  1. **게임이 켜져 있으면 절대 편집하지 말 것.** 메모리에 있던 예전 상태로 그대로 덮어써서 편집이 무효화됨(2026-09-18 실제로 겪음). 반드시 게임을 완전히 종료한 상태에서만 편집.
  2. **폴더 안의 "아무 N개"를 채우는 방식은 위험하다.** 이 게임은 화면에 보이는 카운터가 폴더 내 임의의 N개가 아니라 특정 지정된 퍼즐 ID 집합만 인정하는 것으로 보임(숲길 입구에서 8개 채웠는데 7개만 인정된 사례). **부분적으로 몇 개만 채워야 할 때는 정확한 대상 ID를 알 수 없다면, 안전하게 폴더 전체를 채우는 쪽을 권장.**
  3. 편집 후에는 반드시 게임을 재실행해서 세이브를 다시 불러와야 반영이 확인됨.
  4-1. **저장 시점은 "닫을 때"다 (편지/팝업류 한정).** 편지/팝업 창을 연 상태에서는 디스크의 세이브 파일이 갱신되지 않고(`HasBeenOpened`가 여전히 이전 값), **창을 닫는 순간 디스크에 기록됨**이 실제로 확인됨(2026-09-18, `Data/Tutorial-1`으로 2회 재현 검증 — solved/opened를 강제로 0으로 초기화한 뒤 다시 열고 닫아도 동일하게 재현됨). 편지류 팝업은 닫는 순간 `HasBeenSolved`와 `HasBeenOpened`가 **동시에 true**로 바뀜.
  4-1b. **반면 일반 퍼즐은 여는 즉시(닫기 전에) 저장된다.** `Zone1/8-poly/0365.puz`의 `HasBeenOpened`를 강제로 false로 초기화한 뒤 게임에서 클릭해서 열기만 하고 **창을 닫지 않은 상태**로 세이브 파일을 확인하니 이미 `HasBeenOpened=true`로 기록되어 있었음(2026-09-18 확인). 즉 "닫을 때만 기록"은 편지/팝업 한정 규칙이고, 일반 퍼즐은 여는 즉시 디스크에 반영됨 — 세이브 파일을 실시간으로 폴링하는 경우 퍼즐 진입은 바로 감지할 수 있지만, 편지 열람은 플레이어가 창을 닫아야 감지된다는 차이가 있음.
  4. **화면에 튜토리얼/퍼즐이 "열린 것처럼" 보여도 실제 세이브에는 아직 기록 안 된 경우가 있다** (2026-09-18 여러 차례 확인: 0578/0540, 0609/0665). 플레이어가 근처에 가거나 표지판을 본 것만으로는 저장되지 않고, 실제로 퍼즐을 클릭해서 들어가야 `PuzzleData`에 항목이 생기는 것으로 보임. 사용자가 부른 번호를 세이브에서 못 찾으면 "새 항목 추가"로 처리하면 됨(에러 아님).
  5. **"새 항목 추가" 전에 반드시 기존 존재 여부를 먼저 확인할 것.** 이미 존재하는 경로를 "new"로 또 추가하면 TMap에 같은 키가 중복 생성됨(2026-09-18 실제로 발생: `7-finalboss/1152.puz`). 게임이 이걸 어떻게 처리할지 불확실해서(중복 키는 정상적으로는 불가능한 상태) `set_solved.py remove` 서브커맨드로 중복 중 하나를 안전하게 제거하고 Size/NumEntries 헤더도 같이 보정하는 방식으로 대응함.
  6. **튜토리얼 팝업에 뜨는 이름 ≠ 항상 지역(창) 이름.** `6-compass` 사례에서, 첫 퍼즐을 열었을 때 뜬 "나침반"이라는 이름은 그 안에서 쓰이는 **규칙(메커니즘) 이름**이었고, 실제 지역명(완료 시 뜨는 이름)은 "생울타리 미로"였음. 규칙 이름과 지역 이름이 다를 수 있다는 걸 염두에 두고, **가능하면 튜토리얼 시작 시점보다 지역 완료 시점의 라벨을 더 신뢰할 것.**
